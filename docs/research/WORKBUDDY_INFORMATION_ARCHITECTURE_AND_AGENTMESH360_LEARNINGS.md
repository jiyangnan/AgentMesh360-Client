# WorkBuddy 产品信息架构与 AgentMesh360-Client 借鉴

状态：本机观察记录
观察日期：2026-07-31
观察对象：WorkBuddy 5.3.8
本机安装路径：`/Applications/WorkBuddy.app`
适用项目：AgentMesh360-Client

## 1. 文档目的

本次研究不是为了复制 WorkBuddy 的外观，而是回答两个产品问题：

1. 一个包含任务、助理、项目、技能和自动化能力的桌面 Agent 产品，如何组织一级导航；
2. AgentMesh360-Client 的模型供应商页面，应该如何区分“查看已有配置”和“新增或编辑配置”。

本文严格区分：

- **直接观察**：本机 WorkBuddy 5.3.8 界面中实际可见、可以确认的页面事实；
- **AgentMesh360 设计结论**：结合 AgentMesh360 产品边界得出的适配建议，不代表 WorkBuddy
  的原始设计意图；
- **未观察范围**：本轮没有证据，不能据此推断的内部实现。

## 2. 观察边界与证据纪律

### 2.1 本轮直接核实

- 应用名称：WorkBuddy；
- 版本：5.3.8；
- macOS 本机路径：`/Applications/WorkBuddy.app`；
- 左侧一级入口及其顺序；
- 任务列表与主要工作区的相对位置；
- “专家·技能·连接器”区域采用列表优先、进入二级页面后再配置的页面层级。

### 2.2 本轮没有核实

本轮没有读取 WorkBuddy 源码、网络请求、数据库、凭据存储、进程模型或服务端接口，
因此本文不对以下事项作结论：

- WorkBuddy 的 Agent Harness、调度方式或进程架构；
- 任务、项目、助理是否以何种数据结构持久化；
- 专家、技能和连接器的安装、签名、权限或沙箱机制；
- 模型供应商、API Key、订阅和计费的内部实现；
- 自动化的执行器、触发器和后台恢复机制。

页面观察只能证明产品如何向用户组织信息，不能证明其内部技术架构。

## 3. 直接观察：WorkBuddy 的一级导航

WorkBuddy 左侧导航按以下顺序展示：

1. **新建任务**
2. **助理**
3. **项目**
4. **专家·技能·连接器**
5. **自动化**
6. **更多**

左侧下方继续展示已有任务列表，右侧为当前任务的主要内容区域。版本号
`WorkBuddy v5.3.8` 直接显示在侧栏上方。

### 3.1 可直接确认的产品层级

- “新建任务”是高频动作，不被藏进设置页；
- “助理”与“任务”分开，用户可把持续存在的能力身份和一次具体工作区分开；
- “项目”承担更长期的工作组织，不与单次任务混在同一入口；
- “专家·技能·连接器”被组织为一个能力管理入口，没有把每一种能力都扩展成一级菜单；
- “自动化”作为独立入口，说明用户主动发起的工作和自动触发的工作在产品心智上分开；
- “更多”承接低频能力，避免一级导航继续膨胀。

这些是可见的信息架构事实。它们不说明 WorkBuddy 内部是否使用一个或多个 Agent
进程，也不说明“助理”“专家”或“技能”的技术实现关系。

### 3.2 主工作区与“助理”

本轮可见的主任务工作区采用三段式布局：

1. 左侧为一级导航和最近任务；
2. 中间为当前对话与输入区；
3. 右侧用于当前上下文或产物。

“助理”入口不是一个全局技术设置页。进入一个助理后，默认面向用户的是对话工作区，
页面同时展示该助理已经连接的渠道或能力入口。由此只能确认 WorkBuddy 将“和助理工作”
置于“配置助理技术细节”之前，不能推断其助理进程是否常驻。

## 4. 直接观察：列表优先、配置进入二级页面

在“专家·技能·连接器”相关页面中，默认管理视图优先展示已有项目或能力列表；新增、
选择或进入某个条目后，才进入该条目的二级配置。

可以直接确认的交互原则是：

1. **先回答“我已经有什么”**；
2. **再回答“我要新增或修改什么”**；
3. 配置表单不是管理页的默认主体；
4. 列表负责浏览、定位和进入；
5. 二级页面负责一个具体对象的详细配置。

这种层级让返回页面的老用户先看到已有状态，不必每次先越过一张空白新增表单。
同时，新用户仍可通过明确的新增入口开始配置。

### 4.1 “专家·技能·连接器”的局部导航

进入这个一级入口后，页面内部继续用三个局部页签组织：

- **专家**
- **技能**
- **连接器**

它们共享同一个能力管理领域，但没有把三者的内容混成一张长页面。

### 4.2 专家页

本轮直接看到的专家页包含：

- 搜索；
- “我的专家”；
- 推荐或特色场景；
- 分类页签；
- 专家列表与调用入口。

默认落点是发现和使用专家，不是一个空白“创建专家”表单。

### 4.3 技能页

本轮直接看到的技能页包含搜索、“我安装的 18”和“添加技能”。点击“添加技能”后，
才出现二级菜单：

- 查找技能；
- 上传技能；
- 创建技能。

进入“我安装的”后是独立管理页，包含返回全部技能的层级、已安装数量、批量管理，以及
每行的更多、置顶和启用/停用控件。也就是说，目录浏览、添加方式和已安装对象管理是
三个不同层次，没有同时堆在首屏。

### 4.4 连接器页

本轮直接看到的连接器页以搜索、连接器列表和“自定义连接器”行动组成。每一行先展示
名称、说明和“连接”行动；具体凭据或连接配置只有在用户选择某个连接器后才进入。

这一点与 Provider 管理尤其相关：管理页先回答“有哪些可连接对象、哪些已经配置”，
具体连接表单属于用户主动选择后的下一层。

## 5. 直接观察：页面职责保持单一

从可见导航可以看出，WorkBuddy 没有把所有能力塞进同一个“设置”页面：

- 任务入口处理当前工作；
- 助理入口处理持续能力身份；
- 项目入口处理长期工作组织；
- 专家、技能和连接器入口处理能力扩展；
- 自动化入口处理自动触发的工作；
- 更多承接低频入口。

这里值得借鉴的是“每个一级页面回答一个用户问题”，不是这些名称本身。

## 6. 针对 AgentMesh360-Client 的设计结论

以下内容是针对 AgentMesh360 的设计推导，不是对 WorkBuddy 的继续描述。

### 6.1 不复制 WorkBuddy 的一级导航

AgentMesh360 当前最核心的产品对象是持久 Agent，而不是通用任务工作台。因此不应直接
照搬“新建任务、助理、项目、自动化”六项导航。

AgentMesh360 继续保持以下三个一级入口更符合当前产品边界：

1. **Agent**
2. **模型供应商**
3. **设置**

具体对话、模型绑定、`agent.md` 和 `user.md` 继续属于某个 Agent 的详情。模型供应商页
只负责供应商本身的接入和维护。

### 6.2 模型供应商页必须改为列表优先

模型供应商页面打开后的默认内容应该是“已经配置好的模型供应商”，而不是新增表单。

推荐页面结构：

```text
模型供应商                              [＋ 配置新供应商]
管理 Agent 可使用的模型服务

已配置的模型供应商（N）
┌──────────────────────────────────────────────────────────┐
│ 智谱 GLM Coding Plan   可用   8 个模型   最近验证时间    │
│                                      [编辑] [更多]       │
├──────────────────────────────────────────────────────────┤
│ Google Gemini          需重新验证   4 个模型              │
│                                      [编辑] [更多]       │
└──────────────────────────────────────────────────────────┘
```

默认列表每行优先展示：

- 用户自定义名称和官方供应商名称；
- 当前是否可用，或者为什么需要处理；
- 已验证的模型数量；
- 最近一次验证状态或时间；
- 编辑和更多操作。

协议、认证 Header、Base URL、Key 尾号和三档检查属于二级详情或高级区域，不应让每个
列表条目默认展开成技术控制台。

### 6.3 “配置新供应商”打开独立配置层

点击“配置新供应商”后，再打开独立的配置弹窗。新增和编辑可复用同一套配置组件，但要
使用不同标题：

- 新增：**配置新供应商**
- 编辑：**编辑模型供应商**

弹窗内部继续使用 AgentMesh360 已确定的业务流程：

1. 选择供应商；
2. 输入 API Key；
3. 验证 Key 并动态获取模型；
4. 选择模型；
5. 测试连接；
6. 安全保存。

保存成功后：

- 关闭弹窗；
- 列表立即增加或更新相应条目；
- 清空一次性 Key；
- 给出明确但不遮挡工作的成功反馈；
- 将键盘焦点返回“配置新供应商”按钮或刚编辑的列表条目。

保存失败后：

- 弹窗保持打开；
- 已输入的非秘密字段和当前模型选择保留；
- Key 只保留在当前 Renderer 的临时内存草稿和密码输入值中，不进入 HTML markup、
  日志、磁盘或 Host 持久状态；
- 错误信息说明发生了什么以及如何恢复。

### 6.4 空状态仍然以列表页面为容器

零供应商时不应退回“默认展示一整张表单”。应该显示一个清楚的空状态：

```text
还没有模型供应商
配置一个模型供应商后，Agent 才能选择模型并开始工作。

[配置第一个供应商]
```

这样零个、一个和多个供应商始终共享同一种页面心智，用户不会因为数据数量变化而进入
完全不同的页面结构。

### 6.5 编辑与删除属于具体列表条目

“编辑”从对应列表条目进入二级配置；“删除”放在更多操作或危险操作区。

删除前必须显示：

- 将删除的供应商名称；
- 正在使用该供应商的 Agent；
- 删除后这些 Agent 将无法发送新消息；
- 已有对话不会删除；
- 取消和明确的危险操作按钮。

删除成功后移除列表条目，并让受影响 Agent 进入可理解的模型失效状态。不得静默切换到
其他供应商。

## 7. 可借鉴与不可照搬

| WorkBuddy 直接观察 | AgentMesh360 可借鉴 | 不应照搬 |
|---|---|---|
| 一级入口按用户任务分区 | 每个一级页面只回答一个核心问题 | 直接复制六项导航名称 |
| 助理与任务分开 | 持久 Agent 与具体对话/工作状态分层 | 推断两者的内部进程关系 |
| 专家、技能、连接器合并为能力入口 | 避免未来每个 Agent/Skill 都成为一级菜单 | 把所有扩展能力塞进“设置” |
| 默认先展示已有列表 | Provider、Agent 和未来扩展目录都应浏览优先 | 首屏固定展示新增表单 |
| 进入条目后再配置 | 新增/编辑使用二级配置层 | 复制 WorkBuddy 的具体控件和视觉 |
| 高频与低频入口分层 | 低频诊断继续留在设置或高级区 | 为了相似而增加当前没有的项目/自动化功能 |

## 8. 视觉借鉴边界

本轮只借鉴信息层级和页面职责，不复制 WorkBuddy 的：

- 品牌颜色；
- 字体；
- 图标；
- Logo；
- 阴影、圆角和动效；
- 侧栏宽度与具体间距；
- 列表行的视觉样式。

AgentMesh360 应建立自己的统一设计规范和组件尺度，再用自己的视觉语言实现“列表优先、
二级配置”的结构。

## 9. AgentMesh360 对应测试要求

信息架构调整不能只靠截图验收。至少需要覆盖：

1. 打开模型供应商页时列表优先，新增表单未默认出现；
2. 零供应商显示空状态和“配置第一个供应商”；
3. 单个和多个供应商的列表顺序、状态和操作正确；
4. 点击“配置新供应商”后弹窗打开并获得正确焦点；
5. 真实按钮点击完成 Key 验证、模型选择、连接测试和保存；
6. 保存成功关闭弹窗并更新列表；
7. 保存失败保留可恢复的输入状态；
8. 编辑时公开配置正确预填，已保存 Key 不被读回；
9. 编辑取消不写入 Host；
10. 删除取消、成功、失败和受影响 Agent 提示；
11. Escape、关闭按钮、未保存草稿和焦点恢复；
12. 切换页面、窗口隐藏和后台订阅复验不清空正在配置的草稿；
13. 1180 × 760 的常用桌面窗口首屏能够看到主要列表内容；
14. 字号、控件高度、焦点态和错误态符合 AgentMesh360 自己的设计规范。

测试文档只有在零、单、多条列表以及新增、编辑、删除的真实交互全部执行后，才能把这一
页面职责标记为“通过”。

## 10. 最终结论

WorkBuddy 5.3.8 最值得 AgentMesh360 借鉴的不是白色界面或侧栏样式，而是一条清楚的
产品原则：

> 管理页面先展示用户已经拥有的对象，新增和编辑进入下一层。

对 AgentMesh360-Client 而言，这意味着模型供应商页应从“长表单加附属列表”调整为
“供应商列表加明确新增入口”，配置细节只在用户主动新增或编辑时出现。

这项调整不会改变 Provider Vault、动态模型发现、连接测试、Agent 模型绑定或 BYOK
边界；它只修正页面层级，让用户先看见自己的供应商，再决定是否配置新的供应商。
